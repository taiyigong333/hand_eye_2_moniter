# 标定板映射与手眼结果正确性检查

本文档回答两个问题：

1. 标定板参数确认后，生成的 `aruco_id_map_new.json` 和 `aruco_id_map_new.jpg` 怎么检查是否正确。
2. 手眼标定完成后，`calibration_result.json`、`debug_vis/` 和终端统计怎么检查是否可信。

结论先说清楚：这些检查能证明“当前输入链路内部一致、质量可接受”，但不能替代外部真值验证。真正要证明机器人能用，还需要把外参接入下游流程，在低速和安全距离下做闭环验证。

## 1. 检查标定板映射结果

当前项目的标定板映射由下面的脚本生成：

```powershell
F:\Anaconda\Anaconda3\envs\hand_eye\python.exe tools\make_aruco_id_map.py assets\boards\board.jpg
```

默认输出：

```text
assets/boards/
├── aruco_id_map_new.json
└── aruco_id_map_new.jpg
```

其中：

- `aruco_id_map_new.json` 是后续 `calib.py --id_map_json` 真正读取的运行输入。
- `aruco_id_map_new.jpg` 是人工检查图，不参与后续计算。

## 2. 先看生成命令和终端输出

生成映射时，终端会打印：

```text
[INFO] detected markers: ...
[OK] saved id map: assets\boards\aruco_id_map_new.json
[OK] saved visualization: assets\boards\aruco_id_map_new.jpg
[INFO] mapped ids: ...
[INFO] skipped ids: ...
```

检查重点：

| 项 | 正常表现 | 异常时优先排查 |
| --- | --- | --- |
| `detected markers` | 能检测到大部分或全部 marker | 图像模糊、曝光、反光、字典 `aruco_dict` 错 |
| `mapped ids` | 当前板应接近 150 个 | 四角点击不准、行列数错、`top_left_is_tag` 错 |
| `skipped ids` | 越少越好，少量边缘检测可接受 | `max_cell_dist` 太严、四角顺序错、板图不完整 |
| 保存路径 | 写入 `assets/boards/aruco_id_map_new.json` | 输出到旧文件名或非配置路径 |

如果 `mapped ids` 明显少于预期，不要直接进入手眼标定。先修正板图、四角点或参数后重新生成。

## 3. 检查 `aruco_id_map_new.jpg`

打开：

```text
assets/boards/aruco_id_map_new.jpg
```

图上的含义：

| 图形元素 | 来源 | 含义 | 检查方式 |
| --- | --- | --- | --- |
| 绿色方框 | OpenCV `cv2.aruco.drawDetectedMarkers()` | OpenCV 检测到的 ArUco marker 外边框 | 应贴合 marker 黑色外框；如果明显偏离，说明检测不可靠 |
| marker 角上的小红色方块 | OpenCV `cv2.aruco.drawDetectedMarkers()` | OpenCV 标出的第 0 个检测角点，通常用于显示 marker 朝向和角点顺序 | 它不是映射目标点；如果大量小红方块不在 marker 角上，说明检测有问题 |
| 蓝色点 | 本项目 `tools/make_aruco_id_map.py` | 检测到的 marker 中心 | 应落在对应 marker 中心附近 |
| 红色点 | 本项目 `tools/make_aruco_id_map.py` | 映射后的目标棋盘格中心重新投影回图像的位置 | 应和蓝色点基本重合 |
| 黄色连线 | 本项目 `tools/make_aruco_id_map.py` | 检测中心到映射中心的偏差 | 越短越好；大量长线说明映射或四角点可能错误 |
| 红色文字 | 本项目 `tools/make_aruco_id_map.py` | 类似 `id23->r12c12rot2` 的映射结果 | 行列和旋转应和实体板布局一致 |

这张图有两层信息：

- OpenCV 原始检测层：绿色方框、小红色方块和 marker ID，说明“这张图里检测到了哪个 ArUco，以及它的四角顺序是什么”。
- 本项目映射检查层：蓝点、红点、黄线和红色文字，说明“这个 ArUco ID 被分配到了棋盘的哪个 row/col/rot”。

不要把 marker 角上的小红色方块和“映射后的红色点”混淆。小红色方块是 ArUco 检测角点；红色圆点才是棋盘格中心的映射结果。

按这个顺序看：

1. 绿色方框是否贴合每个 marker 外边缘。若绿框偏离或缺失，先解决图像清晰度、曝光、反光或 `aruco_dict`。
2. 小红色方块是否落在 marker 的一个角上。它用于提示 OpenCV 的角点顺序，不需要和红色圆点重合。
3. 蓝色点和红色点是否基本重合。整体偏移通常说明四角点或行列数有问题。
4. 红色文字里的 `r` / `c` 是否和实体棋盘位置一致。`row=0` 应在最上方，`col=0` 应在最左侧。
5. 是否出现左右镜像、上下翻转或整板旋转。出现这类问题通常是四角点击顺序错。
6. 是否有大量 marker 没有文字标注。大量缺失通常说明 marker 检测失败或 `max_cell_dist` 过滤过严。
7. 同一位置是否被多个 ID 争用。若出现，通常是检测质量或四角透视变换不稳定。

当前项目点击四角的顺序必须是：

```text
左上 -> 右上 -> 右下 -> 左下
```

点的是 20x15 有效棋盘区域外边界，不是纸张外边界。

## 4. 检查 `aruco_id_map_new.json`

当前项目的 JSON 格式是：

```json
{
  "23": [12, 12, 2]
}
```

含义：

- key：marker ID。
- 第 1 个值：`row`，棋盘行号。
- 第 2 个值：`col`，棋盘列号。
- 第 3 个值：`rot`，角点顺序需要循环偏移的次数。

当前默认板的期望范围：

| 项 | 期望 |
| --- | --- |
| ID 数量 | 150 |
| ID 范围 | `0..149` |
| `row` 范围 | `0..14` |
| `col` 范围 | `0..19` |
| `rot` | 当前旧映射中全部为 `2` |
| 重复 cell | 不应存在 |

可以用下面的命令快速检查 JSON：

```powershell
@'
import json
from collections import Counter
from pathlib import Path

path = Path("assets/boards/aruco_id_map_new.json")
data = json.loads(path.read_text(encoding="utf-8"))
values = list(data.values())
cells = [(v[0], v[1]) for v in values]
dups = [cell for cell, count in Counter(cells).items() if count > 1]

print("ids:", len(data))
print("id range:", min(map(int, data.keys())), max(map(int, data.keys())))
print("row range:", min(v[0] for v in values), max(v[0] for v in values))
print("col range:", min(v[1] for v in values), max(v[1] for v in values))
print("rot values:", sorted(set(v[2] for v in values)))
print("duplicate cells:", dups[:10], "count=", len(dups))
print("bad parity:", sum(1 for r, c in cells if (r + c) % 2 != 0))
'@ | F:\Anaconda\Anaconda3\envs\hand_eye\python.exe -
```

当前板 `top_left_is_tag=true`，所以合法 marker 格满足 `(row + col) % 2 == 0`。如果 `bad parity` 不是 0，说明有 marker 被映射到了黑格位置，不能继续使用。

## 5. 映射结果通过标准

一份映射可以继续用于手眼标定，至少要满足：

- `aruco_id_map_new.json` 路径和 `configs/live_collection.example.json` 中的 `calibration.id_map_json` 一致。
- JSON 中 ID 数量、行列范围、重复 cell、奇偶格检查都正常。
- `aruco_id_map_new.jpg` 中绿色方框贴合 marker、蓝色检测中心和红色映射中心整体接近。
- 每个 marker 的行列标注和实体板位置一致，没有镜像或翻转。
- `tag_size`、`cell_size`、`grid_cols`、`grid_rows`、`top_left_is_tag` 和实体板一致。

如果不满足，优先重新生成映射，不要靠调手眼外参补偿错误映射。

## 6. 检查手眼标定输出

实时采集或手动运行 `calib.py` 后，输出目录通常类似：

```text
outputs/live_calibration_YYYYMMDD_HHMMSS/
├── calibration_result.json
├── dynamic_end_camera_poses.json
└── debug_vis/
    ├── 000_end.jpg
    ├── 000_fixed.jpg
    └── ...
```

检查顺序建议固定为：

1. 先确认本轮使用的输入参数。
2. 看样本数和 RMSE。
3. 看 `debug_vis`。
4. 看跨样本一致性统计。
5. 看输出矩阵量级和方向。
6. 最后做机器人闭环验证。

## 7. 确认本轮输入参数

先看本轮配置快照：

```text
data/live_capture/capture_session_config.json
```

或者运行前用 dry-run 检查：

```powershell
F:\Anaconda\Anaconda3\envs\hand_eye\python.exe scripts\collect_and_calibrate.py --dry_run
```

必须确认：

- `fixed_camera_index=1` 对应外部固定相机。
- `end_camera_index=0` 对应末端腕部相机。
- `intr_fixed` 和 `intr_end` 来自本轮实际相机 profile。
- `id_map_json` 指向刚检查通过的 `assets/boards/aruco_id_map_new.json`。
- `tag_size=0.015`、`cell_size=0.019`、`grid_cols=20`、`grid_rows=15` 与实体板一致。

如果输入参数不对，后面所有结果都没有判断意义。

## 8. 看样本数和 RMSE

`calib.py` 运行时会打印每帧类似信息：

```text
[012] end used=..., rmse=... | fixed used=..., rmse=...
```

检查重点：

- `used` 数量不能太少；每张图至少要达到 `--min_tags`，默认 4，但实际越多越稳。
- `rmse` 应明显低于 `--max_reproj_rmse`，当前常用阈值是 `10.0`。
- 如果大量样本被 `skip (rmse too high)`，先排查相机内参、标定板尺寸、`id_map_json`、图像模糊和角点顺序。

终端日志不会自动完整写入 `calibration_result.json`。需要留档时建议这样运行：

```powershell
F:\Anaconda\Anaconda3\envs\hand_eye\python.exe calib.py ... 2>&1 | Tee-Object outputs\my_live_calibration\run.log
```

## 9. 检查 `debug_vis`

打开输出目录里的：

```text
debug_vis/*_end.jpg
debug_vis/*_fixed.jpg
```

图中：

- 绿色点：检测到的 ArUco 角点。
- 红色点：PnP 求得的板位姿重新投影后的角点。

正常表现：

- 绿色点和红色点基本重合。
- 末端相机和固定相机两路都没有系统性偏移。
- 不同样本中，角点覆盖了图像不同区域，而不是总在同一小块区域。

异常表现：

| 现象 | 常见原因 |
| --- | --- |
| 红绿点整体平移 | 内参不匹配、四角/ID 映射错误 |
| 红绿点有旋转错位 | `rot` 错、marker 角点顺序不一致 |
| 图像边缘误差特别大 | 畸变参数或分辨率不匹配 |
| 大量图没有红点或点很少 | marker 检测失败、遮挡、反光、太远 |

`debug_vis` 只证明单帧板位姿估计质量，不单独证明最终手眼外参一定正确。

## 10. 检查 `calibration_result.json`

打开：

```text
calibration_result.json
```

重点字段：

| 字段 | 检查点 |
| --- | --- |
| `num_total_samples` | 本轮读取到的总样本数 |
| `num_valid_samples` | 通过双相机检测和 RMSE 过滤后的样本数 |
| `board_config` | 是否和本轮标定板参数一致 |
| `T_ee_cam_end` | 腕部相机到末端坐标系的外参 |
| `T_base_board` | 标定板到机器人基座坐标系的外参 |
| `T_base_cam_fixed` | 固定相机到机器人基座坐标系的外参 |

基础矩阵检查：

- 每个 `matrix_4x4` 必须是 4x4。
- 最后一行应接近 `[0, 0, 0, 1]`。
- 左上 3x3 旋转矩阵应近似正交，行列式接近 1。
- `translation_xyz_m` 的单位是米，量级应和现场安装位置一致。

可以用下面的命令做基础数值检查：

```powershell
@'
import json
import numpy as np
from pathlib import Path

path = Path("outputs/live_calibration_YYYYMMDD_HHMMSS/calibration_result.json")
data = json.loads(path.read_text(encoding="utf-8"))

for name in ["T_ee_cam_end", "T_base_board", "T_base_cam_fixed"]:
    T = np.array(data[name]["matrix_4x4"], dtype=float)
    R = T[:3, :3]
    t = T[:3, 3]
    print(name)
    print("  t_m =", t)
    print("  det(R) =", np.linalg.det(R))
    print("  orth_err =", np.linalg.norm(R.T @ R - np.eye(3)))
    print("  last_row =", T[3])
'@ | F:\Anaconda\Anaconda3\envs\hand_eye\python.exe -
```

把 `outputs/live_calibration_YYYYMMDD_HHMMSS` 换成本轮真实输出目录。

## 11. 看跨样本一致性统计

`calib.py` 会在终端打印：

```text
T_base_board consistency:
...
T_base_cam_fixed consistency:
...
```

含义：

- `T_base_board`：不同样本通过腕部相机反推出来的固定标定板位姿是否一致。
- `T_base_cam_fixed`：不同样本反推出来的固定相机外参是否一致。

判断原则：

- 平移和旋转离散越小越好。
- 这两个统计如果明显发散，说明输入链路有问题，通常不是最终矩阵可以手工修好的问题。
- 常见根因包括标定板移动、相机支架松动、机器人运动中采样、内参不匹配、样本姿态缺少旋转变化。

注意：当前代码只把一致性统计打印到终端，不写入 JSON。要复查历史结果，必须保存终端日志。

## 12. 检查固定相机外参使用方向

下游固定相机抓取通常使用：

```text
calibration_result.json/T_base_cam_fixed/matrix_4x4
```

含义是：

```text
p_base = T_base_cam_fixed @ p_cam_fixed
```

不要把它当成 `T_cam_fixed_base` 使用。如果下游要从机器人基座转回固定相机，应显式取逆。

不要误用：

- `T_ee_cam_end`：这是末端相机到机器人末端的外参。
- `T_base_board`：这是标定板到机器人基座的位姿，不是固定相机外参。

## 13. 结果通过标准

一轮手眼标定至少要满足：

- 本轮配置、内参、标定板尺寸和 `id_map_json` 已确认正确。
- `num_valid_samples` 足够，且样本姿态包含明显旋转变化。
- 两台相机的 `debug_vis` 红绿点基本重合。
- 大部分样本 RMSE 低于阈值，没有大量高误差样本被过滤。
- `T_base_board consistency` 和 `T_base_cam_fixed consistency` 没有明显发散。
- 三组核心矩阵格式正常，旋转矩阵正交，平移量级符合现场。
- 下游使用的是 `T_base_cam_fixed.matrix_4x4`，方向没有取反。

满足这些条件只能说明结果“可以进入下游验证”。最终仍需要机器人闭环确认。

## 14. 闭环验证建议

把 `T_base_cam_fixed.matrix_4x4` 接入下游抓取或定位流程后，按低风险方式验证：

1. 机器人低速运行，设置安全高度和安全边界。
2. 先只显示或打印相机点转换到 base 后的位置，不直接抓取。
3. 选取固定场景中的已知点，确认转换后的 base 坐标方向和量级合理。
4. 执行空抓或安全高度预抓，观察运动方向是否正确。
5. 再逐步降低到真实抓取高度。

如果闭环方向明显反了，优先检查矩阵方向、相机坐标系约定、单位和下游 TCP 偏置，不要先手工改 `calibration_result.json`。

## 15. 快速问题定位表

| 问题 | 优先看哪里 |
| --- | --- |
| 映射图整体偏移 | 四角点击、`grid_cols`、`grid_rows` |
| 映射图镜像或翻转 | 四角点击顺序 |
| JSON 中 marker 数少 | 板图质量、`aruco_dict`、`max_cell_dist` |
| `debug_vis` 红绿点错位 | 内参、`id_map_json`、`tag_size`、`cell_size`、`rot` |
| 有效样本少 | 遮挡、反光、两台相机未同时看到标定板 |
| 一致性统计发散 | 标定板/相机松动、机器人运动中采样、姿态变化不足 |
| 固定相机抓取位置偏离很大 | `T_base_cam_fixed` 方向、单位、TCP/夹爪偏置、下游坐标链 |
