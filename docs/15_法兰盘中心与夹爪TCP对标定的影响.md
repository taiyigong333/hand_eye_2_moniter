# 法兰盘中心与夹爪 TCP 对标定的影响

本文说明实时采集时 RTDE 读到“法兰盘中心位姿”或“夹爪 TCP 位姿”分别会带来什么影响。这里的关键点是：两者输出都应理解为机器人 `base` 坐标系下的 6D 位姿 `[x, y, z, rx, ry, rz]`，差别不在于坐标系是不是 `base`，而在于这个 `base` 下的位姿描述的是哪个末端参考系。

## 1. 两种输出分别是什么

| 读数类型 | 物理含义 | 数学记号 |
| --- | --- | --- |
| 法兰盘中心位姿 | 法兰盘中心坐标系在机器人 `base` 坐标系下的位置和姿态 | `T_base_flange` |
| 夹爪 TCP 位姿 | 当前夹爪工具 TCP 坐标系在机器人 `base` 坐标系下的位置和姿态 | `T_base_tcp` |

两者都不是局部偏移量，也不是只在工具坐标系下表达的值。它们的平移部分 `x,y,z` 都是对应参考点在机器人 `base` 坐标系下的位置，旋转部分 `rx,ry,rz` 是对应参考坐标系相对 `base` 的旋转向量。

如果夹爪 TCP 相对法兰盘是固定的，二者关系是：

```text
T_base_tcp = T_base_flange @ T_flange_tcp
T_base_flange = T_base_tcp @ inverse(T_flange_tcp)
```

其中 `T_flange_tcp` 是夹爪 TCP 相对法兰盘中心的固定外参。注意这个偏移会随着末端姿态一起旋转，因此不能简单地在 `base` 坐标下给 `x,y,z` 加一个固定向量。

## 2. 当前代码如何使用 RTDE 位姿

当前实时采集链路会把 `pose.json/tcp_pose` 交给 `calib.py`，再由 `tcp_pose_to_T_base_ee()` 转成：

```text
T_base_ee
```

这里的 `ee` 不是强制等于“法兰盘中心”，而是“采集时 RTDE 读到的那个末端参考系”。也就是说：

- 如果采集时保存的是法兰盘中心位姿，`T_base_ee` 实际就是 `T_base_flange`。
- 如果采集时保存的是夹爪 TCP 位姿，`T_base_ee` 实际就是 `T_base_tcp`。

后续手眼标定会求：

```text
T_ee_cam_end
```

所以读哪个末端参考系，最终得到的相机外参就绑定到哪个末端参考系：

| 采集输入 | 标定结果实际含义 |
| --- | --- |
| `T_base_flange` | `T_flange_cam_end`，腕部相机到法兰盘中心坐标系的外参 |
| `T_base_tcp` | `T_tcp_cam_end`，腕部相机到夹爪 TCP 坐标系的外参 |

## 3. 对眼在手上标定的影响

只要整批样本始终使用同一个末端参考系，手眼标定在数学上是自洽的。换句话说，用法兰盘中心可以标定，用夹爪 TCP 也可以标定，关键是不能混用。

选择法兰盘中心的影响：

- 结果更接近机器人机械结构本身，通常不依赖当前夹爪 TCP 怎么定义。
- 后续如果更换夹爪、修改工具 TCP，只要腕部相机和法兰盘的刚性关系没有变，`T_flange_cam_end` 仍然更容易复用。
- 下游抓取如果用夹爪 TCP 控制，需要额外使用 `T_flange_tcp` 把法兰盘目标和夹爪 TCP 目标互相转换。

选择夹爪 TCP 的影响：

- 标定结果直接绑定到当前夹爪 TCP 定义，和下游 `moveL` / `moveJ` 的目标 TCP 更容易对齐。
- 如果示教器里的 TCP 偏置、TCP 方向或夹爪结构改了，旧的 `T_tcp_cam_end` 就不再代表新的 TCP，通常需要重新确认或重新标定。
- 如果采集过程中切换过 TCP，或者一部分样本是法兰盘中心、一部分样本是夹爪 TCP，手眼方程会被破坏，结果会表现为一致性差、外参漂移或固定相机结果被带偏。

## 4. 对固定相机外参的影响

当前 `dual_camera` 流程会先通过腕部相机结果估计标定板在 `base` 下的位置：

```text
T_base_board = T_base_ee @ T_ee_cam_end @ T_cam_end_board
```

如果 `T_base_ee` 和 `T_ee_cam_end` 使用的是同一个末端参考系，那么无论这个参考系是法兰盘中心还是夹爪 TCP，理论上都能得到同一个 `T_base_board`，进而得到同一个 `T_base_cam_fixed`。

问题出在不一致：

- 采集样本保存的是法兰盘中心，却把结果当成夹爪 TCP 外参使用。
- 采集样本保存的是夹爪 TCP，却在后续文档或配置中当作法兰盘中心解释。
- 采集中途修改了示教器 TCP、工具偏置或工具方向。
- 用 `T_base_flange` 和 `T_base_tcp` 之间的关系时，只加平移、不处理旋转。

这些都会让 `T_base_board` 和 `T_base_cam_fixed` 继承系统误差。表现通常不是某一个样本明显坏掉，而是整批样本的位姿一致性变差，下游固定相机到机器人基座的转换出现稳定偏差。

## 5. 对抓取控制的影响

抓取控制最终需要的是机器人控制器能执行的目标 TCP 位姿。固定相机或 GraspNet 给出的抓取点通常不是机器人 TCP 原点，而是物体上的抓取中心或候选夹爪中心。

因此要分清三件事：

| 名称 | 含义 |
| --- | --- |
| 抓取中心 | 视觉算法输出的物体/夹爪接触相关点，通常在相机坐标系中 |
| 法兰盘中心 | 机器人机械法兰参考点 |
| 夹爪 TCP | 控制器运动命令实际追踪的工具中心点 |

如果下游命令让机器人移动“夹爪 TCP”，目标就应该是 `T_base_tcp_target`。如果你先算到的是法兰盘中心目标，则必须用固定工具外参转换：

```text
T_base_tcp_target = T_base_flange_target @ T_flange_tcp
```

反过来，如果你根据抓取中心生成了一个夹爪 TCP 目标，就不要再把它当成法兰盘中心目标发送，否则末端会差出一个工具偏置。这个偏差会随着姿态变化而变化，不能靠固定的 `base` 平移量稳定补掉。

## 6. 推荐做法

优先建议：

1. 标定前明确本轮 `pose.json/tcp_pose` 保存的是 `flange_center` 还是 `gripper_tcp`。
2. 整批样本、标定计算、结果解释和下游抓取配置必须使用同一个末端参考系。
3. 如果希望标定结果长期稳定复用，优先用法兰盘中心作为手眼标定参考系，再单独维护 `T_flange_tcp`。
4. 如果希望和当前夹爪运动命令直接对齐，可以用夹爪 TCP，但要把当前 TCP 名称、偏置和方向写入实验记录。
5. 不要在采集过程中切换示教器 TCP，也不要中途修改工具偏置。

实机前最小检查：

- 在机器人静止时读取一次法兰盘中心位姿和夹爪 TCP 位姿，确认两者都在 `base` 坐标系下表达。
- 记录当前示教器使用的 TCP 名称、TCP 偏置和 TCP 方向。
- 如果能同时拿到 `T_base_flange` 和 `T_base_tcp`，用 `T_base_tcp = T_base_flange @ T_flange_tcp` 检查两者关系是否符合预期。
- 采集完成后，在本轮实验记录或配置快照里写清楚 `tcp_pose_frame`，例如 `flange_center` 或 `gripper_tcp`。

## 7. 已有数据怎么判断

如果已有数据没有记录当时读的是法兰盘中心还是夹爪 TCP，只能回到采集时的机器人设置确认：

- 查看当时示教器当前 TCP 是否为法兰盘中心或某个夹爪 TCP。
- 查看采集脚本是否调用了当前 TCP 读数，还是专门读取了法兰盘位姿字段。
- 对比同一姿态下历史 `tcp_pose` 与当前机器人在相同 TCP 设置下的读数。

如果无法确认，不能把这批外参强行解释成某个具体末端参考系。更稳妥的做法是重新采集，并把 `tcp_pose_frame` 明确记录下来。
